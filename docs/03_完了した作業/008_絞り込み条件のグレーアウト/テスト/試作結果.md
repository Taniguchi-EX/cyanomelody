# 試作結果

## 確かめたこと

3万ファイル・310タグ（最上位10、子50、孫250の3階層）・出典20のデータで、すべての項目の「選んだときの件数」を求める時間を測った（`app/src-tauri/src/facets.rs`の`facet_speed`、リリースビルド）。各ファイルにはタグを3つずつ付けた。

## 結果

### 1回目：すべてSQLで数える
タグの祖先をたどる再帰のSQLと、ファイルの条件を組み合わせて、タグごとに数えた。

| 条件 | 件数の計算 | 一覧（参考） |
|---|---|---|
| 条件なし | 186ms | 120ms |
| 最上位のタグ1つ | 722ms | 170ms |
| タグ2つ | 697ms | 136ms |
| ファイル名 | 102ms | 15ms |
| 出典1つ | 10ms | 6ms |

タグで絞り込んでいるときに目安（0.2秒）を大きく超えた。タグの条件（そのタグか子孫が付いていること）が、ファイルとタグの組ごとに何度も調べられていた。

### 2回目：SQLはファイルを取り出すだけにし、数えるのはメモリの上で行う
- SQLでは、条件に合うファイルのid・出典・ライセンスだけを取り出す。
- ファイルとタグの対応と、タグの親子をまとめて読み、タグごとの件数（祖先にも数える）をメモリの上で数える。
- 同じ条件の問い合わせは1回にまとめる。

最上位のタグ1つで157ms、タグ2つで153msになった。残りはSQLでのタグの条件の調べ方だった。

### 3回目：タグの条件もメモリの上で調べる
SQLにはタグの条件を外して問い合わせ、タグの条件はメモリの上で調べるようにした。

| 条件 | 件数の計算 | 一覧（参考） |
|---|---|---|
| 条件なし | 58ms | 144ms |
| 最上位のタグ1つ | 54ms | 184ms |
| タグ2つ | 39ms | 138ms |
| ファイル名 | 24ms | 16ms |
| 出典1つ | 31ms | 7ms |

## 決めたこと

3回目の方法で実装する。すべての条件で目安の0.2秒を下回り、一覧の読み込みと同じくらいか、それより速い。
件数が実際に絞り込んだ件数と一致することは、単体テスト（いくつかの条件で、各項目を選んで絞り込んだ件数と比べる）で確かめた。
