# 試作結果（性能）

実施日：2026-11-10

## 測ったもの
`cargo test --release draw_speed -- --ignored --nocapture`（`src/playlists/draw_tests.rs`）

- ライブラリ：3万件
- プレイリスト「大量」：3万件が対象のタグの組み合わせ（順に再生）、1万5千件が対象のタグの組み合わせ（🔀）、20曲ずつのプレイリスト50個の参照。抽選すると 46,000 行
- ほかに、20曲ずつのプレイリスト50個（左の欄の通しの曲数の計算に入る）

## 結果（リリースビルド、3回）
| 処理 | 時間 |
|---|---|
| 抽選（展開して一時テーブルに入れる） | 82〜87ms |
| 一覧（46,000行） | 177〜187ms |
| 件数（左の欄の各項目） | 83〜88ms |
| タグで絞り込んだ一覧（30,600行） | 139〜159ms |
| プレイリストの一覧と、全プレイリストの通しの曲数 | 40〜41ms |
| 中身の版 | 1ms 未満 |

## 決めたこと
- 作業概要の「作りの方針」のとおり、抽選した並びを一時テーブルに入れ、絞り込み・件数・並べ替えは SQL でつないで行う形のままでよい。一覧・件数の時間は、3万件のライブラリの一覧と同じ程度。
- 通しの曲数は、プレイリストの一覧を読むたびに数え直す（覚えておく仕組みは作らない）。40ms 程度で、データを読み直すたびに行っても困らない。
- 中身の版は、データを読み直すたびに比べてよい（1ms 未満）。
