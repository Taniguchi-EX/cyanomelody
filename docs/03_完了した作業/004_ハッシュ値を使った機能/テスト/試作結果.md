# 試作結果

確認日：2026-11-02
環境：Windows 11 Home、12スレッドのCPU、Rust 1.98.1

## 1. タグ情報を書き換えてもハッシュ値が変わらないか

テスト用の音源（`app/src-tauri/tests/fixtures`、`tests/make-fixtures.sh`で作成）を使った。形式ごとに以下の3つを用意した。
- base：440Hzの0.3秒の音
- retag：baseをffmpegの`-c copy`で作り直し、タイトルとコメントを変えたもの（音声は同じ）
- other：660Hzの音

結果
- WAV、FLAC、OGG、M4A：最初の実装で、baseとretagが同じ、baseとotherが違うハッシュ値になった。
- MP3：最初の実装では、baseとretagのハッシュ値が違った。
  - 原因：最初のフレームがXing/Infoヘッダ（エンコーダの情報やフレーム数を入れる、音声ではないフレーム）で、ffmpegが作り直すときに大きさと中身を書き換えていた。2番目以降のフレームは完全に同じだった。
  - 対応：最初のフレームがXing/Info/VBRIヘッダなら、対象から除くようにした（`01-01_ハッシュ値の計算方法.md`に追記）。直した後は同じハッシュ値になった。

追加で確かめたこと（テストの中でファイルを組み立てて確認）
- MP3：ID3v2をもう1つ、APEv2、Lyrics3 v2、ID3v1を足しても同じハッシュ値
- WAV：奇数の大きさのLISTチャンクを足しても同じハッシュ値
- FLAC：先頭にID3v2を足しても同じハッシュ値
- 拡張子が違っても（OGGを`.mp3`にしても）、中身で形式を判定して同じハッシュ値
- 壊れたファイルや途中で切れたファイルは、パニックせずにエラーまたは計算結果になる

結果：問題なし（MP3は上記の対応をした後）

## 2. 計算にかかる時間

`cargo test --release hash_speed -- --ignored --nocapture`で測った。

小さいファイル（3KBのMP3）を3万件
- 1スレッド、1回目：26.1秒
- 1スレッド、2回目：1.9秒
- 12スレッド、3回目：0.44秒

1回目だけ遅いのは、作ったばかりのファイルを初めて開くときに、Windows Defenderが検査するためと考えられる（2回目以降は速い）。ファイルを丸ごとメモリに読む工夫をしても、1回目の時間は変わらなかった。

大きいファイル（500MBのWAV）
- 約1,200〜2,000MB/秒（OSのキャッシュに載った状態）

結論
- 計算そのものは十分に速い。時間の大半はファイルを開く処理と、ディスクの読み込みにかかる。
- そのため、計算は複数のスレッドで並列に行う。
- 初めてのスキャンでは、ファイル数や置き場所（外付けHDDなど）によって数十秒以上かかることがありうるため、裏で計算して画面を止めないようにし、中止もできるようにする（概要のとおり）。

結果：問題なし
