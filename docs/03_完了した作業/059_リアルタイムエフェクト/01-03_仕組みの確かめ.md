# 仕組みの確かめ

実機（Android 17、WebView）で、開発版の画面に開発者ツールから試しのコードを流して確かめた。

## 分かったこと
- 曲の audio 要素を `createMediaElementSource` で AudioContext に通すと、無音になる（AnalyserNode で測ると 0）。曲は `http://android-fs-content.localhost/...`（プラグイン tauri-plugin-android-fs のプロトコル）から読んでいて、画面（`http://tauri.localhost`）と別のオリジンになる。プラグインの応答に CORS のヘッダー（Access-Control-Allow-Origin）がないため、ブラウザの決まりで音が消される。`fetch` でも読めない（`no-cors` なら opaque）。
  - プラグインの応答に、外からヘッダーを足す手段はない（応答を作る処理は公開されていない）。
- AudioWorklet は使える（`isSecureContext` は true。Blob の URL からモジュールを読み込めて、処理が呼ばれ続ける）。
- 単発の音：AudioContext で作った音（キック風）を、audio 要素の曲を止めずに重ねて鳴らせる。
- 遅れ：`baseLatency` は 0.005 秒（5ミリ秒）、`latencyHint: "interactive"`。

## 対応：CORS のヘッダーを付けるプロトコル
- エミュレータ（Android 17・x86_64）で確かめた：同じ曲を、プラグインのプロトコルから読んだ audio 要素を AudioContext に通すと無音（peak 0）。`cm-media` から `crossOrigin = "anonymous"` で読むと、音が通る（peak 0.12）。`fetch` でも範囲を指定して読める（206）。

## アプリの再生を cm-media に切り替えた後（エミュレータ）
- Android では、曲もエフェクトの音（`effects-cache` の WAV）も `cm-media` で読み、audio 要素に `crossOrigin = "anonymous"` を付ける（`platform.ts` の `mediaSrc`、`MobileApp.tsx`）。`cm-media` は、`effects-cache` の外のパスは返さない（403）。
- 普段の再生：鳴る（エラーなし）。エフェクトセット（音量 -6dB）をかけた曲も鳴り、AudioContext に通した音の大きさが、かけない曲のほぼ半分（0.119 → 0.060）になる。
- AudioContext に通した後
  - 画面を消してロックしても、曲は進み続け（10秒 → 30秒）、AudioContext は running のまま、音も通っている。再生の通知も PLAYING のまま。
  - ホームに戻ってアプリを裏に回しても同じ。アプリに戻っても続いている。
  - ただし、開発者ツールをつないだまま確かめた。つないでいないときの動きは、最後に実機で確かめる。
- 遅れ（指で触ってから音が変わるまで）は、エミュレータでは分からないので、最後に実機で確かめる。

## 決めたこと
- 曲の音は、ライブの画面を初めて開いたときに AudioContext に通す（`createMediaElementSource` は取り消せないので、開かない人の普段の再生には手を入れない）。一度通したら、アプリを閉じるまで通したままにする。
