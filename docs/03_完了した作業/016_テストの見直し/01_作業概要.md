# テストの見直し

## 目的

テストに時間がかかりすぎて、変更のたびに流すのが重い。次の2つで軽くする。
- 変更したところに関係するテストだけを流せるように分ける。
- 要らないテスト・ほかと重なっているテストを消す。

## 今の状態（6回目の手動UIレビューの反映の時点）

- 単体テスト（Rust、89件）：1秒ほど。型チェック・lint と合わせても速い。
- 画面テスト：10本のスクリプト、156件。合わせて約5分。
  - 長いもの：export（約70秒、6件）、playlists（約60秒、29件）、tag-management（約40秒、32件）
  - 3万件のフォルダを使う、性能を測るテストが4件ある（T16・T17・P17・H10）。
  - 決まった時間だけ待つところ（`waitForTimeout`）が約90か所ある。
- 毎回、画面テストの前にリリースビルドをしている（Rustを変えたときは数分かかる）。
- 単体テスト・ビルド・画面テストをまとめて流す仕組みが、リポジトリになく、作業ごとに手で組み立てている。
- 画面テストの中に、単体テストで既に確かめている中身（データの扱い、絞り込みの計算、名前の決まりなど）を、画面からもう一度確かめているものが多い。

## 方針

### 1. 分けて流せるようにする
- テストを流す入口を1つのスクリプト（`app/check.sh`）にまとめ、流す範囲を選べるようにする。
  - `quick`：単体テスト・型チェック・lint だけ（1分以内）。実装の途中はこれを流す。
  - `e2e <機能名...>`：変更した機能の画面テストだけ（ビルドも含む）。
  - `all`：単体テストと、性能のテストを除くすべての画面テスト。作業の最後（コミットの前）に流す。
  - `perf`：性能のテストだけ。一覧・スキャン・絞り込み・ハッシュ値の計算・プレイリストの展開を変えたときだけ流す。
- 性能のテスト（3万件のフォルダを使う4件）を、新しいスクリプト `perf.mjs` に移す。ほかのスクリプトからは3万件のフォルダを使わない。
- 「変更したもの → 流す画面テスト」の対応表を `開発の手順.md` に書く（例：タグの左の欄を変えたら tags、プレイリストの詳細画面なら playlists）。
- 画面テストのためのビルドを、リリースビルドのままにするか、より速くできるか（デバッグビルドなど）を測って決める。

### 2. 要らないテスト・重なっているテストを消す
次の決まりで、画面テストを1件ずつ見直す。
- 消す：単体テストで同じことを確かめていて、画面で確かめることがない（画面は結果を出すだけ）もの。
  - 例：重複した名前で作れない（`create_rejects_duplicate_ignoring_case` など）、フォルダの登録の制限（`add_folder_rejects_nested_and_duplicate`）、タグのANDやファイル名での絞り込み（`tags_and_filters`・`filter_by_text_ignores_case_and_escapes_wildcards`）、件数の計算（`counts_match_actual_filter_results`）、子孫への統合の禁止、候補が複数のときのひも付け直し、など
- まとめる：同じ画面の流れを別々のテストで少しずつ確かめているもの（見つからないファイルの印・絞り込み・戻す・外す、名前の変更と Enter・Esc、条件のチップと「✕」など）は1件にする。
- 残す：画面にしかない動き（ドラッグ、表示の切り替え、入力欄・ダイアログ、記号の出し方、件数のグレーアウト、再生の欄など）と、機能の主な流れが通ること。
- 消す・まとめる候補は、見直しの結果として一覧（`テスト/見直しの一覧.md`）に、テストごとに「消す（どの単体テストで確かめているか）」「まとめる（どこへ）」「残す」を書く。目安として、画面テストを156件から100件前後にする。

### 3. 待ち時間を減らす
- 決まった時間だけ待つところを、条件を待つ形（処理中の表示が消える、一覧の件数が変わる、など）に置き換える。置き換えられないもの（音を鳴らしている間など）は残す。

### 4. スクリプトの分け方
- tag-admin（タグ自体の管理）と tag-tree（タグの階層）は同じ欄を扱うので、1本（`tags.mjs`）にまとめる（アプリの起動とフォルダの登録が1回で済む）。そのほかのスクリプトの分け方は今のまま。

## やらないこと

- 単体テストを減らすこと（速いので、そのまま）
- テストの仕組み（Playwright で WebView2 につなぐ）を変えること
- 機能の変更

## 目標

- 実装の途中で流すもの（quick）：1分以内
- 1つの機能の画面テスト：ビルドを除いて1分以内
- すべての画面テスト（性能を除く）：ビルドを除いて今の半分（2分半）以内
