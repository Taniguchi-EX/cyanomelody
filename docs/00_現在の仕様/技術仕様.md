# 技術仕様

アプリの構成と使う技術。決めた経緯と試作の結果は `02_完了したタスク/0002_技術選定/` を参照。「」の項目は開発者の確認待ち。

## 構成

1つのアプリの中で層に分ける。サーバは立てない。

```
画面（TypeScript ＋ React、Tauri の WebView）
    │  Tauri のコマンドとイベント
アプリの中核（Rust、OS に依存しない）
  プレイリスト管理、再生順の制御、同期のルール
    ├─ 音楽ソース（共通の窓口）：Google Drive、ローカル
    ├─ 保存：Google Drive 上のプレイリストと設定、端末の SQLite、曲のキャッシュ
    └─ 再生と OS 連携
         音声のデコードと出力（Rust）
         Android のバックグラウンド再生、通知、音声フォーカス、権限、ログイン（Kotlin の Tauri プラグイン）
```

## 使う技術

- アプリの枠組み：Tauri 2
- 言語：Rust（2024エディション）、TypeScript、Kotlin（Androidだけ）
- 画面：React ＋ Vite
- 音声：Symphonia 0.5（デコード）、cpal 0.16（出力）、rubato（サンプルレートの変換）
- タグ：lofty
- HTTP：ureq 2
- 端末のデータ：SQLite（rusqlite）
- Android：最低、対象ともにAPI 37（Android 17）

## Google Drive

- 権限：`drive.readonly`、`drive.file`
- 曲はファイルIDで識別し、Range指定の部分取得で読む。続けて読むときは、まとめて取得する大きさを倍々に増やす（最大4MB）
- プレイリストと設定は、マイドライブ直下の `cyanomelody` フォルダにJSONで保存する
  - `settings.json`：Driveの指定フォルダ、端末IDごとのローカルの指定フォルダ
  - `playlists/<プレイリストID>.json`：プレイリスト1つにつき1ファイル
- ログイン：WindowsとUbuntuはブラウザで同意してループバックで受け取る（PKCE付き）。AndroidはGoogle Identity ServicesのAuthorizationClient
- リフレッシュトークン：WindowsとUbuntuはOSの資格情報の保管庫に保存する
- OAuthクライアント（デスクトップ）のJSONは、リポジトリに入れず、ビルド時に `secrets/google_oauth_desktop.sec.json` から埋め込む
- 曲の読み込みは、前回の続きを読むときにまとめて取得する大きさを倍々に増やし、読み進めたら次の範囲を先に取得しておく
- MP3のシークは、ID3タグの後ろの最初のフレームとXingヘッダの目次（なければ平均ビットレート）から位置を見積もり、そこから読み直す

## 端末に持つデータ

- 端末ID：初回起動時に発行し、アプリのデータ領域に保存する
- SQLite：曲の一覧とタグ情報、曲のキャッシュの索引
- 曲のキャッシュ：アプリのキャッシュ領域。最大容量の既定値は2GB

## ビルド

- Windows版：開発PCでビルドする
- Android版、Ubuntu版：Dockerのビルド環境でビルドする
- アプリのID：`dev.cyanomelody.app`
