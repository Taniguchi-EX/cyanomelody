# 開発の手順

## 構成

- `app/`：アプリ本体
  - `src/`：画面（React、TypeScript、Vite）
  - `src-tauri/`：内部処理（Rust、Tauri 2）
  - `e2e/`：画面テストのスクリプトとテストデータの作成スクリプト

### コードの分け方

- 画面（`src/`）
  - `hooks/useAppController.ts`：データ（フォルダ・タグ・プレイリストなど）と中央の一覧を持ち、読み直し（`reloadAll`）を行う。Windows と Android の画面で共有する。操作は `hooks/` の役割ごとのフック（`useTagActions`・`useCreditActions`・`useLibraryActions`・`usePlaylistActions`・`useEffectChainActions`・`useFileOperations`・`usePlayback` など）に置き、処理中の扱いと結果の表示（`AppOps`：`run`・`showInfo`・`showError`）を渡して使う。
  - `views/`：欄の中身（絞り込みの欄・一覧の欄・詳細の欄・重ねて出す画面）。`useAppController` の結果を受け取る。
  - `App.tsx`：Windows の画面の組み立て（3列と再生の欄）。`mobile/MobileApp.tsx`：Android の画面の組み立て（動的エリアと再生エリア、画面の積み重ねと戻る操作）。`main.tsx` が、Android かどうか（`platform.ts` の `isAndroid`）で選ぶ。
  - 指での操作（長押し・ドラッグの間のスクロールの止め方）は `touch.ts`。Android だけの違いは、部品の中で `isAndroid` を見て分けるか、`mobile/mobile.css`（`.m-app` の中だけに効く）で吸収する。
  - `components/`：画面の部品。1つの部品が長くなったら、行・欄ごとに分ける（例：編集画面の項目の行は `PlaylistItemRow`、項目を加える欄は `PlaylistAddPanel`）。
  - `api.ts`：Rust のコマンドを呼ぶ関数だけ。データの型は `types.ts`、並び順・再生方法の選び肢は `listOptions.ts`、一番下の行に出す文は `statusText.ts`。
- 内部処理（`src-tauri/src/`）
  - `lib.rs`：起動（状態を作り、コマンドを登録する）だけ。状態は `state.rs`。
  - `commands/`：画面から呼ぶコマンド。役割ごとのファイル（`library`・`files`・`tags`・`autotag`・`credits`・`playlists`・`effects`・`data`・`app`）に分け、中の処理は各機能のモジュールを呼ぶだけにする。
  - 裏で行う処理は `*_job.rs`（`hash_job`・`autotag_job`・`export_job`）。
  - ファイルの場所（パスか Android の SAF の URI か）は `location.rs`、ファイルを読む処理が受け取る型は `source.rs`、SAF の操作は `saf.rs`。
  - 機能のモジュールが長くなったら、フォルダにして役割で分ける（例：`transfer/` は形式・書き出し・取り込み、`playlists/` は本体・項目の操作・展開・抽選）。単体テストが長いときは、別のファイル（`*_tests.rs`・`tests.rs`）に置く。

## 必要なもの

- Rust（stable、MSVC）とVisual Studio Build Tools
- Node.js
- WebView2ランタイム（Windows 11には入っている）
- ffmpeg（テスト用の音源やデータを作るときだけ）

## よく使うコマンド

`app/`で実行する。

- 依存関係のインストール：`npm install`
- 開発モードで起動：`npx tauri dev`
- 実行ファイルのビルド：`npx tauri build --no-bundle`
- ライセンスの一覧の作成：`node scripts/licenses.mjs`（ビルドの前と check.sh で自動で行う。下の「ライセンスの一覧の作り方」）
- インストーラのビルド：`npx tauri build`（自動アップデートの署名をするので、環境変数`TAURI_SIGNING_PRIVATE_KEY`に秘密鍵の中身、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`に空文字が要る。下の「公開の手順」）
- README のスクリーンショットの撮り直し：`bash e2e/readme-shots.sh`（見本の効果音を`E:\tmp\見本`に作り、リリース版のアプリで操作して、`assets/readme/`に画像を置く。画面のパスにユーザー名が出ないよう、見本はユーザーのフォルダの外に置く）
- テスト：`bash check.sh <範囲>`（下の「テストの流し方」を参照）
- 単体テストだけ：`src-tauri`で`cargo test`
  - ハッシュ値の単体テストは`src-tauri/tests/fixtures`の音源を使う。作り直すときは`src-tauri`で`bash tests/make-fixtures.sh`（ffmpegが必要）
  - 計測用のテスト（3万ファイルのスキャン、ハッシュ値の計算の速さ、絞り込みの件数の計算の速さ、プレイリストの表示・展開の速さ、抽選した並びの一覧・件数の速さ（draw_speed）、エフェクトの処理の速さ）は`cargo test --release -- --ignored --nocapture`で実行する

## 実行ファイルの場所

`app/src-tauri/target/`の下にできる。`target/`はgitの管理外で、ビルドし直すと上書きされる。

- リリース版：`app/src-tauri/target/release/cyanomelody.exe`
  - `npx tauri build --no-bundle`と`npx tauri build`で作られる。
  - これ1つで起動できる（WebView2ランタイムが必要）。普段使うアプリは、インストーラで入れた版で、これではない。
- 開発版：`app/src-tauri/target/debug/cyanomelody.exe`
  - `npx tauri dev`で作ったものは、画面を開発サーバ（Vite）から読むため、単独では起動しても画面が出ない。
  - `npx tauri build --debug --no-bundle`で作ったものは、画面を埋め込むので単独で動く。画面テストはこれを使う（`check.sh`が作る）。
- インストーラ（NSIS）：`npx tauri build`で作られる。`<版>`は`src-tauri/tauri.conf.json`の`version`。
  - `app/src-tauri/target/release/bundle/nsis/cyanomelody_<版>_x64-setup.exe`

## Android 向けのビルド

Android の SDK・NDK は PC に直接入れず、Docker のイメージに入れる（`app/android/`）。端末で動かすときは、Windows 側の adb（Google の platform-tools）から USB でつないだ実機を使う（Docker の中からは USB の端末が見えず、エミュレータは実用的な速さで動かないため）。

- イメージを作る（初回だけ。JDK 17・Android SDK・NDK r29・Rust の Android のターゲット・Node.js）：`cd app/android && docker build -t cyanomelody-android-build .`
- デバッグ版の APK を作る（リポジトリの一番上で）：`bash app/android/run.sh bash app/android/build.sh aarch64`
  - `run.sh` は、node_modules・cargo・Gradle の置き場所と、APK に署名するデバッグ用の鍵を Docker のボリュームに置く（Windows 用と分けるため。鍵がビルドのたびに変わると、端末の上で更新できない）。
  - 出来上がり：`app/src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk`
- 端末に入れる：`adb install -r <APK>`。Git Bash から adb を使うときは、`export MSYS_NO_PATHCONV=1` をしておく（端末のパス `/sdcard/...` が Windows のパスに書き換えられないように）。
- 画面の確認：デバッグ版の WebView は、開発者ツールにつなげる（`adb forward tcp:9333 localabstract:webview_devtools_remote_<PID>` の後、Playwright の `connectOverCDP`）。
- NDK は r28 以降を使う（共有ライブラリを 16 KB のページサイズに合わせる。Android 15 以降の決まり）。
- デスクトップだけで使うもの（自動アップデート・ごみ箱）は、`Cargo.toml` のデスクトップ向けの依存に置き、コードは `#[cfg(desktop)]` で分ける。
- Android のファイルは、パスでなく SAF の URI で扱う。ファイルを読む処理は、パスではなく `source::FileSource`（`location::Location` が、パスか SAF の URI かを表す）を受け取る。SAF の操作は `saf.rs`（プラグイン `tauri-plugin-android-fs`）にまとめる。

## 環境変数

- `CYANOMELODY_DATA_DIR`：データ（SQLite）の置き場所を変える。テストで普段のデータと分けるときに使う。
- `CYANOMELODY_FAKE_UPDATE`：開発用のビルドで、アップデートの確認でこの版が見つかったことにする（「アップデート」を参照）。`e2e/run.sh`が update.mjs のときだけ`9.9.9`を渡す。
- `CYANOMELODY_DRAW_SEED`：プレイリストの抽選の乱数の種（数字）。画面テストで抽選の結果を毎回同じにするため（`e2e/run.sh`が`1`を渡す）。抽選するたびに種に通し番号を足すので、抽選し直すと結果は変わる。普段のアプリでは使わない。
- `CYANOMELODY_TRASH_DIR`：ファイルの削除で、Windows のごみ箱の代わりにこのフォルダへ移す。画面テストで、使っている PC のごみ箱にテストのファイルがたまらないようにするため（`e2e/run.sh`がテストごとに`<作業用フォルダ>/<テスト名>/trash`を渡す）。このときは、名前（拡張子の前）が`_notrash`で終わるファイルは、ごみ箱に移せないことにする（移せないときの確認を試すため）。普段のアプリでは使わない。

## テストの流し方

`app/`で`bash check.sh <範囲>`を実行する。範囲は次の4つ。

- `quick`：単体テスト（cargo test）・型チェック（tsc）・lint（oxlint）。20秒ほど。実装の途中はこれを流す。
- `e2e <名前...>`：指定した画面テストだけ（例：`bash check.sh e2e tags playlists`）。テストデータの作成とデバッグビルドも行う。変更した機能の画面テストを流すときに使う（下の「画面テスト」の一覧）。
- `all`：`quick`と、性能を除くすべての画面テスト。3分ほど（ビルドを除くと2分ほど）。作業の最後（コミットの前）に流す。
- `perf`：性能の画面テスト（3万件のフォルダ）。1分弱。下の一覧で`perf`に当たる変更をしたときに流す。

- テストデータと結果は`CYANOMELODY_TEST_DIR`（省くと一時フォルダの`cyanomelody-test`）に置く。ログ・スクリーンショット・`results.json`（テストごとの結果と時間）はその下にできる。
- 画面テストはデバッグビルドで流す。リリースビルドより速く作れ、テストの時間はほとんど変わらない。
- 普段使っているアプリ（インストールした版）は止めない（テストのアプリは別の名前・別のデータで動かす）。

## 画面テスト

`app/e2e/`にPlaywrightのスクリプトがある。起動したアプリのWebView2にリモートデバッグでつないで操作する。

### スクリプトと、変更したときに流すもの
「スクリプト名：確かめる機能（この変更をしたときに流す）」。どの範囲でも、最後に`all`を流す。Rustだけの変更で画面に出るものが変わらないときは`quick`でよい。

- `tag-management`：音声のタグ管理（左の欄の検索・条件のチップ、ファイルの一覧、右の欄、欄の幅・たたみ）
- `tags`：タグ自体の管理（作成・名前の変更・削除・統合・階層・並べ替え・ドラッグ）
- `synonyms`：タグのシノニム（詳細画面の一覧・付けるタグ名・左の欄の検索・統合）
- `autotag`：ファイルの情報からのタグ付け（確認のダイアログ・無視する値・区切り文字）
- `hash-features`：ハッシュ値を使った機能（重複・リンク切れ・ひも付け直し・同じ音声で絞り込む）
- `credits`：出典とライセンスの管理（左の欄・フォーム・右の欄の設定）
- `bulk`：ファイルの一括操作（チェック、チェックの操作の行、一括操作の欄、ドラッグでのまとめての操作）
- `facets`：件数とグレーアウト（絞り込みの条件の数え方）
- `playlists`：プレイリスト（左の欄・選んだ一覧と抽選・来た項目のアイコン・編集画面・項目・再生の欄・直近で再生したもの）
- `effects`：エフェクト（エフェクトセットの管理画面・fx のプルダウン）
- `export`：プレイリストの出力（チェックした項目の曲の書き出し）
- `delete`：ファイルの削除（確認のダイアログ・ごみ箱に移せないとき。ごみ箱の代わりのフォルダを使う。上の「環境変数」）
- `settings`：設定画面（タブ・一般・データのエクスポートとインポート・バージョンとライセンス）
- `grid`：グリッドビュー（切り替え・覚えている・タイルの中身・押す・矢印キー・再生・チェックと Shift・ドラッグ）
- `update`：アップデートの確認のダイアログ（見せかけの新しい版 9.9.9。「はい」は押さない）
- `layout`：狭いウィンドウでの表示（再生の欄の配置・ファイルの行のタグのたたみ・管理画面の幅。page.setViewportSize で画面の大きさを変え、各ステップの最初に 1280×800 に戻す）
- `perf`：性能（一覧の表示・スキャン・絞り込みの計算・ハッシュ値の計算・チェックとドラッグの対象の数・プレイリストを選ぶ（抽選）時間と再生し始めるまでの時間。3万件のフォルダを使い、ほかのスクリプトでは3万件を使わない）
- `helpers.mjs`：共通部分（テストではない）

`check.sh`を使わずに流すとき
1. テストデータを作る：`bash e2e/make-testdata.sh <テストデータのフォルダ>`
2. ビルドする：`npx tauri build --debug --no-bundle`
3. 実行する：`CYANOMELODY_EXE=src-tauri/target/debug/cyanomelody.exe bash e2e/run.sh <テストデータのフォルダ> <作業用フォルダ> [スクリプト名...]`
   - スクリプト名を省くと、性能のテストを除くすべてを実行する。
   - テストごとに、空のデータでアプリを起動し直す（データは`<作業用フォルダ>/<スクリプト名>/appdata`、WebView2の保存領域は`webview`）。
   - テストのアプリは、実行ファイルを`<作業用フォルダ>/cyanomelody-e2e.exe`に写して動かし、終わったらそれだけを止める。
   - 実行ファイルは、環境変数`CYANOMELODY_EXE`で変えられる（省くとリリース版）。
   - スクリーンショットと結果（`results.json`）は`<作業用フォルダ>/<スクリプト名>/`に保存する。

### 書き方の決まり
- 決まった時間だけ待つ（`waitForTimeout`）のは、「何も起きない」ことを確かめるとき・音を鳴らしている間・性能の計測だけにする。ほかは条件を待つ。
  - 処理の終わり：`ui.waitIdle`（処理の回数`data-run-count`が増える）
  - 一覧の読み直し：`ui.filtered(操作)`（一覧の版`data-list-version`が増える）
  - 確認のダイアログ：`ui.confirmed(操作)`（ダイアログが出るのを待つ）
  - 下の行の文字：`ui.waitStatus(文字)`
  - 要素が出る・消える：Playwright の`waitFor`
- 単体テストで確かめている中身（名前の重なり、絞り込みの計算など）は、画面テストで確かめ直さない。画面にしかない動き（ドラッグ、表示、入力欄・ダイアログ、記号、グレーアウト、再生の欄など）と、機能の主な流れを確かめる。

確認のダイアログは、Tauriのダイアログのプラグインが`window.confirm`をOSのダイアログ（非同期）に置き換えたもので、テストから操作できない。そのため`helpers.mjs`で、メッセージを記録して決めた答えを返すものに置き換える（`ui.setConfirmReply`で答えを、`ui.lastConfirm`で最後のメッセージを扱う）。画面を読み込み直すときは`ui.reload`を使う（置き換えをやり直すため）。

テストはテストデータのファイルを一時的に移動・名前変更する。途中で止めた場合は、`formats/`のファイルがそろっているか確かめる（`make-testdata.sh`で作り直せる）。

## ライセンスの一覧の作り方

設定画面の「バージョンとライセンス」に出す一覧（「設定画面」を参照）の作り方。
- `app/scripts/licenses.mjs` が、ビルドの前（`npm run build`・`npm run dev`）と、`check.sh` の型チェックの前に、`app/src/generated/licenses.json`（Git の管理外）を作る。
- Rust：`cargo metadata`（Windows 向け）で、アプリから通常の依存をたどったライブラリ。JavaScript：`npm ls --omit=dev`。
- 各ライブラリのフォルダの LICENSE・COPYING・NOTICE・COPYRIGHT・UNLICENSE・AUTHORS などのファイルを読む。同じ文章は1つにまとめて持つ。
- ライセンスのファイルを入れずに配布されているライブラリ（symphonia など）は、ライセンスの種類の標準の文章（`app/scripts/license-templates/`。MPL-2.0・MIT・BSD-3-Clause）を使い、ファイル名の欄に「（標準の文章）」と付ける。MIT・BSD の著作権の行には、そのライブラリの作者（なければ「The <名前> authors」）を入れる。

## 公開の手順

GitHub の Releases で配布する（利用者向けの説明はリポジトリの README.md）。

1. 版を決め、`app/src-tauri/tauri.conf.json`・`app/src-tauri/Cargo.toml`・`app/package.json`の version をそろえる（`app`で`npm install --package-lock-only`をして、`package-lock.json`の版もそろえる）。
2. コミットしてプッシュし、版のタグ（`v1.0.1`など）を付けてプッシュする。
3. GitHub Actions（`.github/workflows/release.yml`）が、Windows でインストーラと自動アップデートの情報（`latest.json`）をビルドし、それらを付けた Release の下書きを作る。
   - タグを押してもビルドが始まらなかったときは、GitHub の Actions の画面で「release」→「Run workflow」を押し、版のタグ（`v1.0.1`など）を入れて手動で始める。
4. GitHub の画面で下書きを確かめ、変更点を書いて公開する。公開すると、配布済みのアプリが起動したときに新しい版を見つける（下書きのままでは見つけない）。

### 自動アップデートの署名の鍵
- 更新ファイルは、専用の鍵で署名する（偽物の更新を入れないため）。公開鍵は`tauri.conf.json`の`plugins.updater.pubkey`にある。
- 秘密鍵は`C:\Users\tnms\.tauri\cyanomelody-updater.sec.key`（リポジトリの外。パスワードなし）。GitHub のリポジトリのシークレット`TAURI_SIGNING_PRIVATE_KEY`にも、同じ中身を登録してある。
- 秘密鍵を無くすと、配布済みのアプリに更新を届けられなくなる。別の場所にもバックアップを置いておく。
