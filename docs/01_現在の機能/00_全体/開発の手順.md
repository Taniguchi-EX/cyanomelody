# 開発の手順

## 構成

- `app/`：アプリ本体
  - `src/`：画面（React、TypeScript、Vite）
  - `src-tauri/`：内部処理（Rust、Tauri 2）
  - `e2e/`：画面テストのスクリプトとテストデータの作成スクリプト

## 必要なもの

- Rust（stable、MSVC）とVisual Studio Build Tools
- Node.js
- WebView2ランタイム（Windows 11には入っている）
- ffmpeg（テスト用の音源やデータを作るときだけ）

## よく使うコマンド

`app/`で実行する。

- 依存関係のインストール：`npm install`
- 開発モードで起動：`npx tauri dev`
- 実行ファイルのビルド：`npx tauri build --no-bundle`
- ライセンスの一覧の作成：`node scripts/licenses.mjs`（ビルドの前と check.sh で自動で行う。「設定画面」の「ライセンスの一覧の作り方」）
- インストーラのビルド：`npx tauri build`（自動アップデートの署名をするので、環境変数`TAURI_SIGNING_PRIVATE_KEY`に秘密鍵の中身、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`に空文字が要る。下の「公開の手順」）
- README のスクリーンショットの撮り直し：`bash e2e/readme-shots.sh`（見本の効果音を`E:\tmp\見本`に作り、リリース版のアプリで操作して、`assets/readme/`に画像を置く。画面のパスにユーザー名が出ないよう、見本はユーザーのフォルダの外に置く）
- テスト：`bash check.sh <範囲>`（下の「テストの流し方」を参照）
- 単体テストだけ：`src-tauri`で`cargo test`
  - ハッシュ値の単体テストは`src-tauri/tests/fixtures`の音源を使う。作り直すときは`src-tauri`で`bash tests/make-fixtures.sh`（ffmpegが必要）
  - 計測用のテスト（3万ファイルのスキャン、ハッシュ値の計算の速さ、絞り込みの件数の計算の速さ、プレイリストの表示・展開の速さ、エフェクトの処理の速さ）は`cargo test --release -- --ignored --nocapture`で実行する

## 実行ファイルの場所

`app/src-tauri/target/`の下にできる。`target/`はgitの管理外で、ビルドし直すと上書きされる。

- リリース版：`app/src-tauri/target/release/cyanomelody.exe`
  - `npx tauri build --no-bundle`と`npx tauri build`で作られる。普段使うアプリはこれ。
  - これ1つで起動できる（WebView2ランタイムが必要）。
- 開発版：`app/src-tauri/target/debug/cyanomelody.exe`
  - `npx tauri dev`で作ったものは、画面を開発サーバ（Vite）から読むため、単独では起動しても画面が出ない。
  - `npx tauri build --debug --no-bundle`で作ったものは、画面を埋め込むので単独で動く。画面テストはこれを使う（`check.sh`が作る）。
- インストーラ：`npx tauri build`で作られる。名前の数字はバージョン（`src-tauri/tauri.conf.json`の`version`）。
  - `app/src-tauri/target/release/bundle/nsis/cyanomelody_0.1.0_x64-setup.exe`
  - `app/src-tauri/target/release/bundle/msi/cyanomelody_0.1.0_x64_en-US.msi`

## 環境変数

- `CYANOMELODY_DATA_DIR`：データ（SQLite）の置き場所を変える。テストで普段のデータと分けるときに使う。
- `CYANOMELODY_TRASH_DIR`：ファイルの削除で、Windows のごみ箱の代わりにこのフォルダへ移す。画面テストで、使っている PC のごみ箱にテストのファイルがたまらないようにするため（`e2e/run.sh`がテストごとに`<作業用フォルダ>/<テスト名>/trash`を渡す）。このときは、名前（拡張子の前）が`_notrash`で終わるファイルは、ごみ箱に移せないことにする（移せないときの確認を試すため）。普段のアプリでは使わない。

## テストの流し方

`app/`で`bash check.sh <範囲>`を実行する。範囲は次の4つ。

- `quick`：単体テスト（cargo test）・型チェック（tsc）・lint（oxlint）。20秒ほど。実装の途中はこれを流す。
- `e2e <名前...>`：指定した画面テストだけ（例：`bash check.sh e2e tags playlists`）。テストデータの作成とデバッグビルドも行う。変更した機能の画面テストを流すときに使う（下の対応表）。
- `all`：`quick`と、性能を除くすべての画面テスト。3分ほど（ビルドを除くと2分ほど）。作業の最後（コミットの前）に流す。
- `perf`：性能の画面テスト（3万件のフォルダ）。1分弱。下の対応表で「性能」に当たる変更をしたときに流す。

- テストデータと結果は`CYANOMELODY_TEST_DIR`（省くと一時フォルダの`cyanomelody-test`）に置く。ログ・スクリーンショット・`results.json`（テストごとの結果と時間）はその下にできる。
- 画面テストはデバッグビルドで流す。リリースビルドより速く作れ、テストの時間はほとんど変わらない。普段使うアプリ（リリースビルド）は、作業の最後に1回だけビルドする。
- 普段使っているアプリは止めない（テストのアプリは別の名前・別のデータで動かす）。ただしリリースビルドは、普段のアプリを開いたままだと失敗する。

### 変更したもの → 流す画面テスト

どの範囲でも、最後に`all`を流す。

- 左の欄の検索・条件のチップ、ファイルの一覧、右の欄（ファイルの詳細・タグを付ける欄）、欄の幅・たたみ：`tag-management`
- タグの左の欄（作成・名前の変更・削除・統合・階層・並べ替え・ドラッグ）：`tags`
- ハッシュ値・重複・リンク切れ・ひも付け直し・同じ音声で絞り込む：`hash-features`
- 出典・ライセンス（左の欄・フォーム・右の欄の設定）：`credits`
- チェック、チェックの操作の行、ドラッグでのまとめての操作：`bulk`
- 件数とグレーアウト（絞り込みの条件の数え方）：`facets`
- プレイリスト（左の欄・詳細画面・項目・再生の欄・直近で再生したもの）：`playlists`
- エフェクト・エフェクトセットの管理画面・fx のプルダウン：`effects`
- プレイリストの書き出し：`export`
- ファイルの削除（確認のダイアログ・ごみ箱に移せないとき）：`delete`
- 性能（一覧の表示・スキャン・絞り込みの計算・ハッシュ値の計算・チェックとドラッグの対象の数・プレイリストの展開）：`perf`
- Rustだけの変更で画面に出るものが変わらないとき：`quick`

## 画面テスト

`app/e2e/`にPlaywrightのスクリプトがある。起動したアプリのWebView2にリモートデバッグでつないで操作する。

- `tag-management.mjs`：音声のタグ管理
- `tags.mjs`：タグ自体の管理と、タグの階層構造
- `hash-features.mjs`：ハッシュ値を使った機能
- `credits.mjs`：出典とライセンスの管理
- `bulk.mjs`：ファイルの一括操作
- `facets.mjs`：絞り込み条件のグレーアウト
- `playlists.mjs`：プレイリスト
- `effects.mjs`：エフェクト
- `export.mjs`：プレイリストの出力
- `delete.mjs`：ファイルの削除（ごみ箱の代わりのフォルダを使う。上の「環境変数」）
- `perf.mjs`：性能（3万件のフォルダ。ほかのスクリプトでは3万件を使わない）
- `helpers.mjs`：共通部分

`check.sh`を使わずに流すとき
1. テストデータを作る：`bash e2e/make-testdata.sh <テストデータのフォルダ>`
2. ビルドする：`npx tauri build --debug --no-bundle`
3. 実行する：`CYANOMELODY_EXE=src-tauri/target/debug/cyanomelody.exe bash e2e/run.sh <テストデータのフォルダ> <作業用フォルダ> [スクリプト名...]`
   - スクリプト名を省くと、性能のテストを除くすべてを実行する。
   - テストごとに、空のデータでアプリを起動し直す（データは`<作業用フォルダ>/<スクリプト名>/appdata`、WebView2の保存領域は`webview`）。
   - テストのアプリは、実行ファイルを`<作業用フォルダ>/cyanomelody-e2e.exe`に写して動かし、終わったらそれだけを止める。
   - 実行ファイルは、環境変数`CYANOMELODY_EXE`で変えられる（省くとリリース版）。
   - スクリーンショットと結果（`results.json`）は`<作業用フォルダ>/<スクリプト名>/`に保存する。

### 書き方の決まり
- 決まった時間だけ待つ（`waitForTimeout`）のは、「何も起きない」ことを確かめるとき・音を鳴らしている間・性能の計測だけにする。ほかは条件を待つ。
  - 処理の終わり：`ui.waitIdle`（処理の回数`data-run-count`が増える）
  - 一覧の読み直し：`ui.filtered(操作)`（一覧の版`data-list-version`が増える）
  - 確認のダイアログ：`ui.confirmed(操作)`（ダイアログが出るのを待つ）
  - 下の行の文字：`ui.waitStatus(文字)`
  - 要素が出る・消える：Playwright の`waitFor`
- 単体テストで確かめている中身（名前の重なり、絞り込みの計算など）は、画面テストで確かめ直さない。画面にしかない動き（ドラッグ、表示、入力欄・ダイアログ、記号、グレーアウト、再生の欄など）と、機能の主な流れを確かめる。

確認のダイアログは、Tauriのダイアログのプラグインが`window.confirm`をOSのダイアログ（非同期）に置き換えたもので、テストから操作できない。そのため`helpers.mjs`で、メッセージを記録して決めた答えを返すものに置き換える（`ui.setConfirmReply`で答えを、`ui.lastConfirm`で最後のメッセージを扱う）。画面を読み込み直すときは`ui.reload`を使う（置き換えをやり直すため）。

テストはテストデータのファイルを一時的に移動・名前変更する。途中で止めた場合は、`formats/`のファイルがそろっているか確かめる（`make-testdata.sh`で作り直せる）。

## 公開の手順

GitHub の Releases で配布する（利用者向けの説明はリポジトリの README.md）。

1. 版を決め、`app/src-tauri/tauri.conf.json`・`app/src-tauri/Cargo.toml`・`app/package.json`の version をそろえる（`app`で`npm install --package-lock-only`をして、`package-lock.json`の版もそろえる）。
2. コミットしてプッシュし、版のタグ（`v1.0.1`など）を付けてプッシュする。
3. GitHub Actions（`.github/workflows/release.yml`）が、Windows でインストーラと自動アップデートの情報（`latest.json`）をビルドし、それらを付けた Release の下書きを作る。
   - タグを押してもビルドが始まらなかったときは、GitHub の Actions の画面で「release」→「Run workflow」を押し、版のタグ（`v1.0.1`など）を入れて手動で始める。
4. GitHub の画面で下書きを確かめ、変更点を書いて公開する。公開すると、配布済みのアプリが起動したときに新しい版を見つける（下書きのままでは見つけない）。

### 自動アップデートの署名の鍵
- 更新ファイルは、専用の鍵で署名する（偽物の更新を入れないため）。公開鍵は`tauri.conf.json`の`plugins.updater.pubkey`にある。
- 秘密鍵は`C:\Users\tnms\.tauri\cyanomelody-updater.sec.key`（リポジトリの外。パスワードなし）。GitHub のリポジトリのシークレット`TAURI_SIGNING_PRIVATE_KEY`にも、同じ中身を登録してある。
- 秘密鍵を無くすと、配布済みのアプリに更新を届けられなくなる。別の場所にもバックアップを置いておく。
