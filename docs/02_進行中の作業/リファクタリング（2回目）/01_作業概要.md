# リファクタリング（2回目）

## 目的

1回目のリファクタリング（010）のあと、プレイリストの項目の別名・エフェクト・出力・UIの改善・手動UIレビューの反映で、コードが大きく増えた（App.tsx 約1,300行、playlists.rs 約1,550行）。
動きを変えずに、読みやすく直しやすいコードにする。

## 進め方

- 「レビュー → 実装 → コミット」を10周行う。周ごとに観点を変える（データ構造、保守性、共通化、処理の分割単位、処理速度など）。
- 各周の観点は、始める前にコードを読んで決める。直したことは、ロードマップの「各周の記録」に書く。
- 周ごとに `bash check.sh quick`（単体テスト・型チェック・lint）を流してからコミットする。
- 10周の後に、セルフレビューと、すべてのテスト（`check.sh all` と `check.sh perf`）を行う。

## やらないこと

- 動きの変更（見つけた不具合は、動きを変えずに直せるものだけ直し、記録する。仕様に関わるものはユーザーに相談する）
- データベースの形の変更（移行が要るもの）
- ライブラリの入れ替え

## 前提・未決事項

- 画面テストで確かめている動きが変わらないこと（画面テストの書き換えは、部品の名前など見た目に出ないものの変更に合わせるときだけ）。
