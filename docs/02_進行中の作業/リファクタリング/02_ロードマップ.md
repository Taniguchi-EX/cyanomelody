# ロードマップ

各周の観点は、始める前にコードを読んで決めた。周ごとに、単体テスト（`cargo test`）、型の確認とlint（`npx tsc -b`、`npx oxlint src`）、リリースビルドでのすべての画面テスト（`e2e/run.sh`）を行う。

- [x] 1周目：画面の共通化（木の並べ替え・開閉の状態の記憶）
- [x] 2周目：データ構造（並べ替えの移す先の型の名前）
- [x] 3周目：App.tsxの分割（再生・チェックの処理を切り出す）
- [x] 4周目：Rust側の共通化（idの一覧の渡し方、絶対パスの組み立て、存在の確認）
- [x] 5周目：コメントの正確性・冗長性

## 各周の記録

### 1周目：画面の共通化
- 観点：同じ処理が画面の部品ごとに書かれていないか。
- 直したこと
  - タグの欄の並べ替え（ドラッグ）の処理を、プレイリストの欄で作った共通の処理`useTreeDrag`（`treeDrag.ts`）に寄せた。行の目印を`data-tree`・`data-node-id`に、一覧の下の空いた所の目印を`data-tree-root`にそろえた。
  - 開閉の状態を覚える処理（タグの欄・プレイリストの欄・各欄のたたみ）が3か所にあったので、`storage.ts`の`useStoredFlag`・`useStoredIdSet`にまとめた。保存の形はこれまでと互換（たたんだ欄の"1"・"0"も読める）。
  - 木の表示の補助（子を持つ節、子孫、たたんだ節を除いた表示）を、タグ専用の`tagTree.ts`から、タグ・プレイリストに共通の`tree.ts`に移した。
  - 行の開閉の印と並べ替えの取っ手を、部品`Twisty`・`DragHandle`（`TreeParts.tsx`）にした。
- 動きの変化：なし。
- テスト：単体テスト64件、画面テスト114件、すべて成功。

### 2周目：データ構造
- 観点：画面と内部処理の間で受け渡すデータの形が、使い方に合っているか。
- 直したこと
  - 並べ替えの移す先（`MoveTarget`）の項目名が`tagId`のままプレイリストにも使われていたので、`id`に変えた。型は、タグとプレイリストに共通のものとして`tree.rs`に移した。
  - ファイルに付いたタグを、名前だけの並びから、idと名前の組（`NamedRef`）の並びにした。右の欄でタグを外すときに、名前からidを探し直す処理がなくなった。`NamedRef`はプレイリストの項目と共通にした。
  - タグの並び順を引く表（`tag_rank`）を、名前ではなくidで引くようにした。プレイリストの項目のタグの並べ替えも、同じ表を使うようにした。
- 動きの変化：なし。
- テスト：単体テスト64件、画面テスト114件、すべて成功。

### 3周目：App.tsxの分割
- 観点：1つのファイル（App.tsx、約1,000行）に、性質の違う処理が詰め込まれていないか。
- 直したこと
  - 試聴とプレイリストの連続再生（audio要素、再生順、飛ばす処理、一時停止）を、フック`useAudioPlayer`（`hooks/useAudioPlayer.ts`）に切り出した。再生の状態を表す型`Player`もここに移した。
  - ファイルのチェック（範囲のチェック、表示中のすべてのチェック、チェックしたファイルの内訳、消えたファイルをチェックから外す処理）を、フック`useChecks`（`hooks/useChecks.ts`）に切り出した。
  - 描画のたびにrefへ書き込んでいた箇所（lintの警告3件）を、状態を変える関数の中か、effectの中で書き込むようにした。
  - ファイルの一覧と編集画面を切り替える部分の字下げを直した（プレイリストの作業のセルフレビューで記録したもの）。
  - App.tsxは約1,000行から885行になった。
- 残した警告：最初の読み込みのeffect（データを読み込んで状態に入れる）と、仮想リストのライブラリについての警告。どちらも作りによるもので、動作に問題はない。
- 動きの変化：なし。
- テスト：単体テスト64件、画面テスト114件、すべて成功。

### 4周目：Rust側の共通化
- 観点：内部処理（Rust）で、同じ書き方が何か所にも繰り返されていないか。
- 直したこと
  - idの一覧をSQLの1つの引数（JSONの配列）にする処理が、`files.rs`の関数と`playlists.rs`の直書き2か所にあったので、`db::ids_json`にまとめた。
  - 行があるかの確認（`SELECT EXISTS ...`）を`db::exists`にまとめた。
  - ライブラリフォルダのパスと相対パスから絶対パスを作る処理が、ファイルの一覧・ハッシュ値の計算待ち・プレイリストの再生順の3か所にあったので、`library::absolute_path`にまとめた。
  - ファイルの並び順（フォルダ、相対パス）を書いたSQLが4か所にあったので、定数`files::FILE_ORDER`にした。
- 動きの変化：なし。
- テスト：単体テスト64件、画面テスト114件、すべて成功。

### 5周目：コメントの正確性・冗長性
- 観点：コメントが今の動きと合っているか。機能を足していくうちに古くなったものや、使われていないコードがないか。
- 直したこと
  - 複数選択をやめた後も「選んだファイル」と書いていたコメント（出典・ライセンスの設定、ハッシュ値の計算の後の読み直し）を、「指定したファイル」「右の欄のファイル」に直した。
  - 機能を足しても書き足されていなかったコメントを直した。
    - フォルダの登録解除：消えるものに、出典・ライセンスの設定とプレイリストの項目を足した
    - ひも付け直し：移すものに、出典・ライセンス・プレイリストの項目を足した
    - タグの削除：プレイリストのタグの組み合わせからも外れることを足した
    - 名前の決まり：プレイリストにも使うことを足した
    - タグでの絞り込みの条件：「すべてのタグが付いた」から「選んだタグごとに、そのタグか子孫が付いた（AND）」に直した
    - `files.rs`の説明に、チェックしたファイルの内訳を足した。ファイルの絶対パスの用途を「試聴」から「再生」に直した
  - 使われていない関数`findByName`（`credits.ts`）を消した。
- 動きの変化：なし。
- テスト：単体テスト64件、画面テスト114件、すべて成功。

### 6周目：機能レベルの微修正（キーボードでの操作）
- 観点：入力欄やダイアログで、キーボードの操作が欄ごとにばらばらになっていないか。
- 直したこと（動きが変わる）
  - タグ・出典・ライセンスの管理画面は、フォーカスが管理画面の中にあるときしかEscで閉じなかった（「タグ自体の管理」のテストで「画面の改善」に回すと記録していたもの）。フォーカスがどこにあってもEscで閉じるようにした（フック`useEscape`）。
    - タグの名前の変更中のEscは、変更をやめるだけにする（入力欄でEscを止める）。
    - 出典・ライセンスの編集中のEscは、編集をやめる（作成のフォームに戻る）だけにする。
  - 出典・ライセンスの管理画面で、名前・URLの欄でEnterを押すと作成（編集中は保存）するようにした。
  - プレイリストの編集画面で、名前の欄と子のプレイリストの名前の欄でEnterを押すと、名前の変更・子の作成をするようにした。ほかの入力欄（タグの付ける、フォルダの登録など）と同じ操作にそろえた。
  - 「01_現在の機能」の「タグ自体の管理」「出典とライセンスの管理」「プレイリスト」に反映した。
- テストの追加：tag-admin.mjsのA11（Escで閉じる、名前の変更中のEsc）、credits.mjsのC20（Enterで作成、Escで編集をやめる・閉じる）、playlists.mjsのP18（Enterで名前の変更・子の作成）。
- 途中の失敗：A11で、名前の変更中のEscで管理画面まで閉じた。Reactが入力欄のEscの処理の直後に描画し直すため、ウィンドウのEscの処理からは「変更中でない」と見えていた。入力欄でEscを止めるようにした。
- テスト：単体テスト64件、画面テスト117件（3件増）、すべて成功。

### 7周目：問い合わせの回数（プレイリストの展開・表示の速さ）
- 観点：項目ごとにデータベースへ問い合わせて、項目の多いプレイリストで遅くなっていないか。
- 直したこと
  - プレイリストの展開（再生順を決める）・ファイル数の計算・編集画面の表示で、項目ごとにファイルの見つからない印・タグの組み合わせのタグ・プレイリストの名前を問い合わせていた。必要なもの（項目、項目のタグ、項目が指すファイル、プレイリストの名前）を最初にまとめて読む`Catalog`を作り、その上で処理するようにした。
  - 同じタグの組み合わせが何度出てきても、対象のファイルを問い合わせるのは1回にした。
  - 計測用のテスト`playlist_speed`（`playlists.rs`、手動で実行）を加えた。3万ファイル、項目1,010件（子のプレイリスト10、各タグの組み合わせ5）のプレイリストで測った。

| 編集画面の表示 | 358ms | 97ms |
| 展開（7万7千曲） | 437ms | 184ms |

- 画面テストのP17（3万件のタグの組み合わせの再生開始）は、全体の実行で345msと出たが、もう2回実行すると262ms・233msで、これまで（218〜250ms）と変わらなかった。ばらつきと判断した。
- テスト：単体テスト64件、画面テスト117件、すべて成功。

### 8周目：型の安全性
- 観点：データベースの文字列と、内部処理の列挙型の変換で、おかしな値を黙って別の値として扱っていないか。
- 直したこと
  - プレイリストの項目の種類（`kind`）と再生方法（`mode`）を、文字列から変換するときに、決まっていない文字列を黙って「プレイリスト」「順に再生」として扱っていた。rusqliteの変換（`FromSql`・`ToSql`）を実装し、決まっていない文字列はエラーにした。文字列と列挙型の対応は1か所（マクロ`sql_text_enum!`）に書く。
  - 項目を加える処理で、種類を文字列（`"file"`など）で渡していたのを、列挙型で渡すようにした（書き間違えるとコンパイルで分かる）。
  - 単体テストを加えた（データベースに決まっていない再生方法が入っていると、エラーになる）。
- 動きの変化：正しいデータでは変わらない。壊れたデータでは、別の値として扱わずにエラーを出す。
- 画面テストのP17（3万件のタグの組み合わせの再生開始）の時間のばらつきを調べた。
  - 7周目以降、全体の実行で335〜380ms、単独の実行で233〜262msとばらついた（6周目までは218〜250ms）。
  - 3万件を展開する処理だけを測る計測用のテスト`tag_combo_speed`を加え、7周目の前のコードと比べた。前が72〜78ms、今が75〜77msで変わらなかった。ばらつきは、内部処理ではなく、3万件を画面に渡して表示するところで出ている。
  - P17は、フォルダを登録した直後（裏でハッシュ値を計算し、終わると3万件の一覧を読み直す）に測っていた。計算と読み直しが終わるのを待ってから測るようにした（それでも238〜380msのばらつきは残った）。
- テスト：単体テスト65件（1件増）、画面テスト117件、すべて成功。
