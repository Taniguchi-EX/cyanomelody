# セルフレビュー

テストの前に、実装を作業概要と突き合わせ、コードを見直した。

## 作業概要との突き合わせ

作業概要の仕様の項目ごとに確かめた。下の「見つけて直した問題」の1つ目を除き、実装されていた。
- プレイリストの名前の決まりと一意、作成（最上位の最後、子として）、名前変更、削除（子の繰り上げ、参照の削除、確認のメッセージ）
- 項目の3つの種類と、抽象的な項目の3つの再生方法。同じ項目を何度でも入れられる
- 階層：子は親の項目として、並びの位置と再生方法を持つ。参照は左の欄の階層に出ない。左の欄での並べ替え（前・後ろ・子の最後・最上位の最後）と、開く・たたむ（状態の記憶）
- ループの防止：項目の追加・左の欄の並べ替えとも、画面で防いだうえで、保存の処理でも確かめる
- 編集画面：名前、項目の一覧（種類、内容、再生方法、ファイル数）、取っ手での並べ替え、外す（子は最上位へ）、タグの組み合わせの追加（選んで加える・いまの絞り込みのタグを加える）、プレイリストの追加、子のプレイリストを作る
- ファイルの追加：一括操作の欄と右の欄の「プレイリストに追加」
- ほかの機能との関係：ファイルがライブラリから消えると項目が外れる、見つからないファイルの表示と再生時の除外、ひも付け直しでの付け替え、タグの削除・統合での組み合わせの更新
- 再生：左の欄と編集画面の再生ボタン（編集画面ではプレイリスト自体の再生方法を選べる）、再生の欄（名前・何曲目か・ファイル名・前へ・次へ・一時停止・停止）、連続再生、最後で止まる、再生できないファイルを飛ばして表示する、試聴で止まる

## 見つけて直した問題

1. 項目を追加する画面で、ループになるプレイリストを候補から外していた。作業概要は「グレーアウトして選べないようにする」なので、候補に出したうえで選べないようにし、「（ループになるため選べません）」と書き添えた。
2. 再生順を決めるときに、ファイルのパスを1件ずつ問い合わせていた。3万件が対象のタグの組み合わせで遅くなるおそれがあるので、まとめて1回で引くようにした。

## 作業概要に書いていなかったが決めたこと

- 使われていないタグの一括削除で、プレイリストのタグの組み合わせで（子孫を含めて）使われているタグは消さない。消すと組み合わせが変わってしまうため。
- 左の欄の各プレイリストの数字は、項目の数（再生したときのファイル数ではない）。ファイル数は、展開するまで決まらない項目（ランダムセレクトなど）があるため。

## 確かめて問題がなかった点

- ループの判定は、項目（子・参照）をたどった到達できるプレイリストの集合で行う。SQLの再帰はUNIONで重複を除くので、万一ループのデータがあっても止まる。展開と件数の計算も、たどっている途中のプレイリストを二重にたどらない。
- 子のプレイリストを左の欄で親の中で動かすときは、親の項目をそのまま使うので、再生方法を引き継ぐ（単体テストで確認）。
- 1つのプレイリストを子にできるのは1か所だけであることを、データベースの一意の索引でも保証している。

## 気づいたが直さなかった点

- App.tsxで、ファイルの一覧と編集画面を切り替える部分の字下げが崩れている。リファクタリングで直す。
- 左の欄のタグの並べ替えと、プレイリストの並べ替えのドラッグの処理が重複している（プレイリストの方は共通の処理`treeDrag.ts`として作った）。タグの方を共通の処理に寄せるのは、リファクタリングで行う。
- 並べ替えの移す先を表す型（MoveTarget）の項目名が`tagId`のままで、プレイリストにも使っている。リファクタリングで名前を直す。
