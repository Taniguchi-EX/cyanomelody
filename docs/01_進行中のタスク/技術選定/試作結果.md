# 試作結果

`試作検証項目.md` の項目を試作で確かめた結果。試作のコードはリポジトリの `prototypes/` にある。

## 2026-10-26：ストリーミング再生、音声形式、タグの部分読み込み

対象の項目：C-4（ストリーミング再生とシーク）、B-2（3つの音声形式とシーク）、C-5（タグの読み込み）の一部

### 方法

- 試作：`prototypes/stream_decode/`
- Google Driveの代わりに、ファイルの一部だけを返せる（Range指定に対応した）HTTPサーバをDockerで立て、そこから曲を読み込んだ。Google Driveのファイルのダウンロード（`files.get` の `alt=media`）もRange指定に対応しているため、同じ作りで読める見込み
- 曲のファイルは、指定した大きさ（32KB、64KB、256KB）ずつ必要な部分だけ取得し、取得済みの部分は使い回す
- ライブラリ：デコードにSymphonia 0.5、タグの読み込みにlofty 0.22
- テスト用の曲：3分、ステレオ、44.1kHz。日本語のタグ（曲名、アーティスト、アルバム）付き
  - MP3（固定ビットレート192kbps）、MP3（可変ビットレート）
  - WAV（タグあり、タグなし）
  - `.m4a`（曲の情報がファイルの先頭にある形式、末尾にある形式）
- 音を実際に鳴らす部分（出力）はDockerの中では確かめられないため、デコードまでを確かめた

### 結果

- 6つのファイルすべてで、部分的な取得だけで、タグの読み込み、再生開始、シーク、最後までのデコードができた
- 日本語のタグを正しく読めた。WAVのタグ（INFO形式）も読めた。タグのないWAVは「タグなし」と判定でき、ファイル名で表示する仕様どおりに扱える
- `.m4a` で曲の情報がファイルの末尾にある形式も、末尾を先に取得して再生できた。最初の音までの通信は、先頭にある形式より1回多いだけだった
- シークの精度：どの形式も、指定した位置の0.1秒以内に着地した

取得単位を64KBにしたときの通信の回数と量：

| ファイル | タグの読み込み | 最初の音まで | 120秒へシーク |
|---|---|---|---|
| MP3（固定） | 2回 124KB | 1回 64KB | 43回 2,752KB |
| MP3（可変） | 2回 77KB | 1回 64KB | 24回 1,536KB |
| WAV | 1回 64KB | 1回 64KB | 2回 128KB |
| `.m4a`（情報が先頭） | 1回 64KB | 3回 141KB | 1回 64KB |
| `.m4a`（情報が末尾） | 3回 142KB | 4回 206KB | 1回 64KB |

### 分かった課題

- MP3は、前方へシークすると、シーク先までのデータをすべて取得する。Symphonia 0.5のMP3の読み込みが、先頭から順にたどって位置を探すため
  - 3分の曲で120秒へ飛ぶと、約1.5〜2.7MBを取得する。回線が遅いと、シークに数秒かかる見込み
  - 一度取得した部分は使い回すので、後方へのシークは通信なしで済む
  - 対策の案：ビットレートや、可変ビットレートのMP3が持つ位置の目次（Xingヘッダ）からファイル上の位置を見積もり、その位置から読み込みを始め直す処理を自前で作る。MP3はどこからでも読み始められる形式なので実現できる見込み。MVPでは許容し、後で改善してもよい
- タグの読み込みの通信量は、取得単位に比例する。単位を小さくすると通信量は減るが、回数が増える
  - 64KB単位なら1曲あたり1〜3回、80〜140KB。1,000曲で約2,000回、約120MB
  - Google Driveの1回の通信に0.2秒かかるとすると、1件ずつ順に処理して約7分、8件ずつ並行して処理すれば約1分の見込み
  - 曲にアルバムアートが埋め込まれている場合、タグが大きくなり通信量が増える（アルバムアートは表示しないが、読み飛ばすにもタグの大きさ分の取得が必要になる場合がある）
- 取得単位は、タグの読み込みでは小さめ（32〜64KB）、再生では大きめ（256KB程度）と使い分けるのがよい

### 判定

- C-4：合格。ストリーミング再生とシークは、Range指定による部分的な取得で実現できる。MP3の前方へのシークだけ、通信量が多いという課題がある
- B-2：デコードとシークは合格。音の出力は、実機またはデスクトップで別途確かめる
- C-5：部分的な取得でタグを読めることは確認できた。所要時間は、Google Driveの実際の応答時間で別途確かめる

### まだ確かめていないこと

- 本物のGoogle Driveでの動作（ログインが必要。C-1、C-2と合わせて確かめる）
- 音の出力（cpal）。WindowsとUbuntuではデスクトップで、Androidでは実機で確かめる

## 2026-10-26：Windowsでの音の出力

対象の項目：B-1（WindowsとUbuntuで同じコードで鳴らせるか）のWindows部分

### 方法

- 試作：`prototypes/play_local/`
- Symphonia 0.5でデコードし、cpal 0.15で既定の出力先から鳴らす。音量はアプリ内で掛け算して変える
- 3秒のチャイム音（MP3、WAV、`.m4a`）を、開発PC（Windows 11）で鳴らした

### 結果

- 3つの形式とも、Windowsの標準の音声の仕組み（WASAPI）で、エラーなく最後まで再生できた
- 出力先のサンプルレートは48kHzで、曲の44.1kHzと違った。WASAPIは出力先のサンプルレートでしか受け付けないため、アプリ側でサンプルレートを変換する必要がある。試作では簡単な変換（線形補間）を自作したが、本番では音質のよい変換ライブラリ（rubatoなど）を使うのがよい
- 3つの形式とも、チャイム音が正しく聞こえることを開発者が耳で確かめた

### 判定

- B-1（Windows）：合格。Ubuntuは、音の出る環境で別途確かめる

## 2026-10-26：Android 17向けのビルド

対象の項目：G-1（Android 17向けのビルド）。A-1（RustからAndroidで音を鳴らせるか）のうち、ビルドが通るところまで

### 方法

- ビルド環境：`prototypes/android_env/`（Dockerfile）
  - Ubuntu 24.04、JDK 17、Node.js 22、Rust（最新の安定版）
  - Android SDK Platform 37.0（Android 17）、Build-Tools 37.0.0、NDK 30.0.16248370
- 試作：`prototypes/tauri_android/`
  - Tauri 2.12の雛形に、チャイム音を鳴らすボタンを足した。押すと、アプリに埋め込んだMP3をSymphoniaでデコードし、cpal 0.16で鳴らす
  - 最低対応バージョンを、Android 17（API 37）にした

### 結果

- Android 17向け（最低対応、対象ともにAPI 37）のAPKを、ARM64向けにビルドできた。所要時間は約5分（初回。依存の取得を含む）
- Tauriの雛形は、最初からAndroid 17（compileSdk 37）向けの設定で生成された。Android Gradle Pluginは9.3.1
- NDK 29にはAndroid 17向けのコンパイラがなく、ビルドに失敗した。NDK 30が必要
- cpal 0.16は、Android標準の音声の仕組み（AAudio）を直接使う。C++の追加ライブラリ（`libc++_shared.so`）は不要で、APKに含める手間がない
- デバッグ版のAPKは約160MB。大半はデバッグ用の情報で、リリース版では大きく減る見込み（未確認）
- 開発PCのDockerではKVMが使えず、Androidエミュレータは動かせない。動作の確認は実機で行う

### 判定

- G-1：合格。ビルド、実機へのインストール、起動ができた。上書きインストールは、次の節で確認した
- A-1：合格。RustでデコードしたMP3を、cpal（AAudio）から出力でき、音も聞こえた

### 実機での確認（2026-10-26）

- 端末：Pixel 10（Android 17、API 37、arm64-v8a）
- PCのadb（SDK Platform-Tools 37.0.1）でAPKをインストールし、起動できた
- 「チャイムを鳴らす」を押すと、画面に「再生中: AAudio / 44100Hz 2ch F32」と表示された
- ログでは、AAudioの出力を開く、再生を始める、閉じる、の各段階がすべて正常に終わった。アプリは落ちなかった
- 出力先は曲と同じ44.1kHzで開かれ、Windowsと違ってサンプルレートの変換は不要だった（低遅延の経路ではなく通常の経路で開かれた。音楽の再生には問題ない）
- チャイム音が正しく聞こえることを、開発者が耳で確かめた

### 実機で確かめる手順

1. Android 17の端末で「開発者向けオプション」の「USBデバッグ」を有効にし、PCとUSBでつなぐ
2. `prototypes/tauri_android/out/cyanomelody-proto-debug.apk` を端末に入れる（`adb install`、またはファイルを端末にコピーして開く）
3. アプリを起動し、「チャイムを鳴らす」を押して、ド・ミ・ソの音が鳴るか、画面に出力先の情報が表示されるかを見る

## 2026-10-26：Android実機でのまとめての確認

対象の項目：G-1（上書きインストール）、E-2（端末の識別）、D-1、D-2（ローカルファイル）、A-5（音量）、A-2とA-6の下調べ

### 方法

- 端末：Pixel 10（Android 17、API 37）。PCとUSBでつなぎ、adbで操作した
- 試作アプリ（`prototypes/tauri_android/`）に、次の機能を足した
  - 長時間再生：チャイムと3秒の無音を、止めるまで繰り返す。10秒ごとに、音の出力が動いた回数をログに出す
  - 曲の一覧と再生：指定したフォルダとサブフォルダの曲を、普通のファイルパスで一覧にし、選んだ曲を再生する
  - 端末ID：アプリのデータ領域に端末IDを保存し、既にあればそれを表示する
- 音楽ファイルを読む権限（`READ_MEDIA_AUDIO`）をアプリに宣言した。権限の付与は、試作ではadbで行った
- テスト用の曲として、チャイム音（MP3、WAV、`.m4a` 2種）を、日本語のフォルダ名とファイル名で端末の `Music/cyanomelody_test/` に置いた

### 結果

上書きインストール（G-1）

- 最初は上書きインストールが「署名が一致しない」として拒否された。ビルドに使うデバッグ用の署名鍵が、Dockerの中でビルドのたびに新しく作られていたため
- 署名鍵をDockerのボリュームに保存して使い回すようにすると、上書きインストールでき、アプリのデータ領域のファイルも残った
- 本番の開発でも、署名鍵を固定し、なくさないように保管する必要がある。鍵が変わると、アンインストールしてから入れ直すしかなく、端末のデータ（端末ID、キャッシュ、設定）が消える

端末の識別（E-2）

- アプリのデータ領域（`/data/user/0/dev.cyanomelody.proto/`）に保存した端末IDは、上書きインストールの後も同じ値で読めた
- アンインストールするとデータ領域は消えるため、端末IDも変わる。この場合の扱い（前の端末IDで追加したローカルの曲がすべてグレーアウトになる）は未決のまま

ローカルファイル（D-1、D-2）

- 音楽ファイルを読む権限があれば、Rustから普通のファイルパス（`/storage/emulated/0/Music/...`）で、フォルダをたどって曲を一覧にし、開いて再生できた。Storage Access Frameworkの独自の形式（`content://`）を使わずに済む
- 日本語のフォルダ名とファイル名（`サブフォルダ/チャイム（末尾moov）.m4a` など）も正しく扱えた
- MP3、WAV、`.m4a`（曲の情報が末尾にある形式を含む）のすべてを再生できた
  - 途中、`.m4a` が再生できなかったが、試作アプリでSymphoniaのAACとMP4の機能を有効にしていなかったためで、有効にすると再生できた
- 権限がないときは、エラーにならず「0曲」になる。本番では、権限の有無を確かめ、ない場合は利用者に許可を求める画面が必要になる。許可を求める処理はKotlin側で作る
- 権限は、上書きインストールの後も残った
- この権限で見えるのは音声ファイルだけで、端末に元からあった録音ファイルも一覧に出た。指定フォルダだけを読む仕様なので問題はない

音量（A-5）

- Rustから鳴らした音は、Androidで「メディア」の音（`USAGE_MEDIA`）として扱われた
- 再生中に本体の音量ボタンを押すと、メディアの音量が変わった（13→12→13）。OSの音量と連動させる仕様は、特別な作りなしで満たせる

バックグラウンド再生の下調べ（A-2）

バックグラウンド再生の仕組み（フォアグラウンドサービス）を入れていない状態での動き。

- ホームに戻った場合：約70秒は再生が続いたが、その後Androidがアプリのプロセスを凍結し、音が止まった。アプリを前面に戻すと凍結が解け、再生が再開した
- アプリを前面に出したまま画面を消した場合：2分以上再生が続き、プロセスは凍結されなかった
- 他のアプリを使っている間も再生を続けるには、フォアグラウンドサービスが必須だと確認できた

他のアプリの音との関係の下調べ（A-6）

- 端末で他のアプリにチャイムを再生させようとしたが、「どのアプリで開くか」の選択画面で止まり、確かめられなかった
- 今の試作は、Androidの「音声フォーカス」（どのアプリが音を鳴らすかの調整の仕組み）を要求していない。そのため、他のアプリが音を鳴らしたり電話がかかってきたりしても、一時停止されずに鳴り続ける見込み。本番では、フォアグラウンドサービスと合わせて、Kotlin側で音声フォーカスを扱う必要がある

### 判定

- G-1：合格。署名鍵の固定が必要
- E-2：上書きインストールで端末IDが残ることは合格。アンインストールした場合の扱いは要件として未決
- D-1：合格。音楽ファイルを読む権限とファイルパスで読める。権限を求める処理はKotlinで作る
- D-2：Androidでは合格。WindowsとUbuntuは未確認
- A-5：合格
- A-2：フォアグラウンドサービスが必須であることを確認した。実装しての確認はこれから
- A-6：未確認。音声フォーカスを扱う必要があることが分かった

## 2026-10-27：バックグラウンド再生、通知とロック画面からの操作、音声フォーカス

対象の項目：A-2（画面を消しても再生を続けられるか）、A-3（通知とロック画面から操作できるか）、A-4（画面に戻ったときに状態がそろうか）、A-6（他のアプリの音との関係）

### 方法

- 端末：Pixel 10（Android 17、API 37）。スキル `cyanomelody-android-test` の手順で、adbから操作した
- 試作アプリ（`prototypes/tauri_android/`）を次の作りにした
  - Rust：常駐する再生エンジン。出力のストリームは開いたままにし、止めているときは無音を流す。プレイリスト（音の高さを変えたチャイム3曲）の再生、一時停止、次の曲、前の曲、停止を受け付ける。状態が変わると Kotlin に知らせる
  - Kotlin（`RustBridge.kt`）：JNIでRustとつなぐ。Kotlin → Rust は `nativeCommand`、Rust → Kotlin は `onStateChanged` の呼び出し
  - Kotlin（`PlaybackService.kt`）：フォアグラウンドサービス（種類 `mediaPlayback`）。Android標準のMediaSessionとメディア形式の通知を出し、音声フォーカスを扱う。追加のライブラリ（Media3など）は使っていない
  - 画面：再生の状態を1秒ごとに表示する

### 結果

Rust と Kotlin のつなぎ（JNI）

- Kotlin → Rust、Rust → Kotlin の両方向の呼び出しができた。Rust の独自のスレッドから Kotlin を呼ぶには、起動時に Kotlin から呼ばれた関数の中で、Javaの実行環境とクラスを控えておく必要がある（試作では `nativeInit` で行った）
- 曲が変わるたびに、Rust から Kotlin に知らせが届き、通知とロック画面の曲名が更新された

バックグラウンド再生（A-2）

- プレイリストの再生を始めると、フォアグラウンドサービスが前面の状態（種類 `mediaPlayback`）で動いた
- ホームに戻った場合：2分以上再生が続いた。プロセスは凍結されなかった（フォアグラウンドサービスの状態）。サービスなしでは約70秒で凍結されていた
- 画面を消した場合：2分以上再生が続いた

通知とロック画面からの操作（A-3）

- 通知に、曲名、アーティスト名、「一時停止（再生）」「前のトラック」「次のトラック」のボタンが出た。ボタンはAndroidがMediaSessionの状態から自動で作る
- ロック画面にも、同じ内容とボタンが出た
- 通知とロック画面のそれぞれで、一時停止、再生、次の曲、前の曲を押し、どれもRustの再生エンジンに届いて状態が変わった
- 通知の表示の権限（`POST_NOTIFICATIONS`）を与えていなくても、メディアの通知は表示された。メディアの通知はこの権限の対象外のため

画面に戻ったときの表示（A-4）

- バックグラウンドで一時停止された後にアプリの画面に戻ると、「チャイム（ミ） / 一時停止 / 2曲目」と、Rust の状態どおりに表示された
- 試作では画面が1秒ごとにRustへ状態を問い合わせている。本番では、Rust から画面に変化を知らせる作りにする

他のアプリの音との関係（A-6）

- 再生中に「Files by Google」で音声ファイルを開いて再生させると、このアプリは音声フォーカスを失った知らせ（`AUDIOFOCUS_LOSS`）を受け、自動で一時停止した
- 一時的に失った場合（電話の着信など、`AUDIOFOCUS_LOSS_TRANSIENT`）に一時停止し、取り戻したら再開する作りも入れたが、一時的に失う状況を作れず未確認
- 端末がロックされていると、他のアプリの画面が開かず音も鳴らないため、この確認はロックを解除した状態で行う必要があった

停止

- 画面の「停止」で、フォアグラウンドサービスが終わり、通知も消え、音声フォーカスも手放した

### 判定

- A-2：合格。Kotlinのフォアグラウンドサービスで、他のアプリを使っている間も画面を消している間も再生が続く
- A-3：合格。通知とロック画面の操作がRustに届く
- A-4：合格
- A-6：他のアプリに音声フォーカスを取られたときの一時停止は合格。一時的に失ったときの動きは未確認
- 主軸の構成（Tauri 2、Rustの中核 ＋ Web技術の画面）で、Androidのバックグラウンド再生を実現できる。Kotlinで書く部分は約200行で、追加のライブラリは不要だった

### 本番に向けて分かったこと

- 試作では、Tauriが生成したAndroidのプロジェクト（`gen/android`）にKotlinのファイルを直接足した。本番では、Tauriのプラグインとして分けると、生成し直したときに消えずに済む
- 出力のストリームを開いたままにして無音を流しているため、一時停止中も電池を使う。本番では、一時停止が続いたらストリームを閉じる
- 一時停止中もフォアグラウンドサービスを前面の状態のままにしている。Androidでは、バックグラウンドからフォアグラウンドサービスを始め直すことに制限があるため。長く一時停止したままのときの扱いは、本番で決める
