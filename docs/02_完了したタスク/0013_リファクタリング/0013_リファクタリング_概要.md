# リファクタリング

## 概要

Android の実機での確認のあと、コード全体を次の観点で見直し、「見直す → 直す → コミットする」を直すところがなくなるまで繰り返した（2026-10-27）。

- 保守しやすいか、インデントが深すぎないか、関数や文が長すぎないか
- 後の開発で役に立たないコメント、冗長なコード、共通化できていない重複がないか
- 役割の分け方が適切か、処理の遅いアルゴリズムになっていないか
- 仕様と食い違う実装がないか、安全な作りになっているか

## 結果

### 1 巡目（コミット 9b99be0）

- 並行処理の共通部品（`parallel::map_parallel`）を作り、タグの読み込みとプレイリストの一覧の取得で使う
- 再生エンジンの、再生できない曲を飛ばす処理を 1 か所にまとめる
- フォルダの中身を、SQL で範囲を絞って読む（全曲を読んでから絞っていた）
- アプリの中核（`AppCore`）の音楽ソースの扱いと、オフラインのときの端末に保存した内容の返し方を整理する
- 画面：設定の画面を部品に分ける、フォルダを選ぶ部品を共通化する、再生中だけ再生位置を問い合わせる
- 安全のため、CSP を設定し、使っていない権限とプラグインを外す

### 2 巡目（コミット e8abf74）

- ライブラリの手動更新を、一覧の振り分けと書き込みに分ける
- Drive の指定フォルダの一覧を、同じ深さのフォルダごとに並行して問い合わせる
- 動作確認用の例（examples）の Drive への接続を共通化する
- 曲の追加画面：フォルダごと追加したときの曲数の数え方を直す、一覧を読めないときに知らせる

### 3 巡目（コミット 06d48df）

- 長い処理を分ける：再生エンジンの命令処理、ログインの待ち受け、Android の通知の更新
- I/O のエラーから Drive のエラーへの変換を共通化する
- 不具合を直す：フォルダを選ぶ画面で、読み込みに失敗すると操作できなくなっていた
- 手動更新の結果に、タグを読めなかった曲の数を出す

### 4 巡目（コミット 39bf758）

- キャッシュが最大容量の内に収まっているときは、追い出す曲の一覧を読まない

### 安全面で確かめたこと（直す必要はなかった）

- 共有されたプレイリストの相対パスから、端末の指定フォルダの外のファイルを開けない
- Drive の検索条件に入れる名前と ID はエスケープしている

### 直さなかったもの

50 行前後の関数がいくつか残る（テスト用の Drive の模擬サーバの振り分け、出力先を開く処理など）。それぞれ 1 つの役割にまとまっており、分けるとかえって読みにくくなるため、このままにした。

## 確認

各巡で次を行った。

- `app/scripts/check.sh`（整形、Clippy、Rust のテスト、TypeScript の型の検査）
- Docker での Android のビルド
- Windows の画面の自動操作による確認（`npm run e2e`）
- 3 巡目は、Android の通知を作り直したため、実機で通知と操作（一時停止・次の曲・停止）を確かめた
