# アーキテクチャ方針

## 方針

1つのアプリの中で、画面とそれ以外の処理を分ける。サーバは立てない。

## 層の分け方

```
画面
  プレイリスト一覧、編集、フォルダ選択、再生画面、設定
    │
アプリの中核（OSに依存しない）
  プレイリスト管理、再生順の制御（シャッフル、リピート、再生できない曲を飛ばす、一周したら止める）
  同期のルール（読み直し、後から保存した方を正とする）
    │
    ├─ 音楽ソース（共通の窓口で抽象化する）
    │    Google Drive、ローカル ……将来ほかのソースを足す
    ├─ 保存
    │    Google Drive上のプレイリストと設定、端末の曲のキャッシュと曲の一覧のキャッシュ
    └─ 再生とOS連携（OSごとに中身が違う）
         音声の再生、Androidのバックグラウンド再生と通知、音量の扱い
```

## この分け方にする理由

- 音楽ソースを共通の窓口（曲の一覧を取る、タグを読む、曲を読み込む）で扱えば、ソースを足すときに他の層を触らずに済む。アプリの目的が「なるべく多くのソースから」なので、ここが一番変わりやすい
- OSによる違い（Androidのバックグラウンド再生、音量の扱い、PCでウィンドウを閉じたら止める）を「再生とOS連携」の層に閉じ込め、それ以外を1つのコードベースで共通にする
- 再生順の制御は画面がなくても動く必要がある（Androidの通知から「次の曲」を押した場合など）。中核に置き、画面からも通知からも同じ処理を呼ぶ

## 主軸とする構成

Rustの中核 ＋ Web技術の画面（Tauri 2）。

- 画面より下の層をRustで書き、画面はWebView上のWeb技術で書く
- Androidのバックグラウンド再生と通知は、Kotlinでプラグインを書いてRustの中核とつなぐ。一度作れば手を入れる機会は少ないと見込む

対抗となる構成との比較は `技術候補の比較.md` を参照。
