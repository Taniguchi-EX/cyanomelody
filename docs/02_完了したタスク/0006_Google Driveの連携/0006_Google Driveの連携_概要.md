# Google Driveの連携

## 概要

Google Drive にログインし、指定フォルダの曲を音楽ソースとして読めるようにする。

詳しい仕様は `00_現在の仕様/機能仕様.md` と `00_現在の仕様/技術仕様.md`、順番は `00_現在の仕様/開発ロードマップ.md` を参照。

## 結果

中核のクレート（`app/crates/core/src/`）:

- `drive/client.rs`：Drive API の呼び出し口 `DriveClient`。フォルダの直下の一覧（ページをまたぐ）、パスでのフォルダの検索、ファイルの情報、Range 指定の部分取得。接続を使い回す。401 で拒否されたら、アクセストークンを更新して 1 回だけやり直す。通信できないときは `DriveError::Network` にする
- `drive/reader.rs`：部分取得しながら読む読み込み口 `RangeReader`。前回の続きを読むときは取得する大きさを倍々に増やし（最大 4MB）、取得した範囲の後半まで読み進めたら次の範囲を別のスレッドで先に取得する。手元に持つのは最大 32MB で、読んでいる位置から遠いものから捨てる
- `drive/auth.rs`：デスクトップのログイン `LoopbackLogin`（ブラウザで同意し、`127.0.0.1` で認可コードを受け取る。PKCE と state の照合付き）と、リフレッシュトークンからアクセストークンを得て期限の 1 分前まで使い回す `RefreshingToken`。リフレッシュトークンが失効していたら消して、ログインし直してもらう
- `source/drive.rs`：Drive の音楽ソース `DriveSource`。指定フォルダとサブフォルダを、ファイル ID で見分けて一覧にする。タグは 64KB 単位、再生は 256KB 単位で読む
- `playback/mp3.rs`：MP3 のシークの位置の見積もり。ID3v2 タグを飛ばして最初のフレームを探し、Xing ヘッダの目次（なければ読んだ範囲のフレームの平均ビットレート）から位置を求める。`playback/decode.rs` で、MP3 はこの位置から開き直してシークする
- `drive/mock.rs`：テスト用の、Drive の応答を真似る HTTP サーバ
- `examples/drive.rs`：本物の Drive でライブラリの更新と再生を確かめる確認用のプログラム

アプリ（`app/src-tauri/src/`）:

- `drive.rs`：リフレッシュトークンを OS の資格情報の保管庫に保存する `KeyringStore`（Windows は資格情報マネージャー、Ubuntu は Secret Service。Android では使わない）と、ログインの状態 `DriveAuth`
- コマンド：`drive_login`（ブラウザを開いてログイン）、`drive_logout`、`drive_logged_in`。画面からの呼び出しは `画面` のタスクで作る
- OAuth クライアント（デスクトップ）の JSON は、ビルド時に `secrets/google_oauth_desktop.sec.json` から埋め込む。リポジトリには入れない。ファイルがなければ、ログインできない版としてビルドされる

### レビュー

- 差分を読み直し、仕様（指定フォルダとサブフォルダ、ファイル ID での識別、通信できないときにライブラリを変えない）との対応を確かめた
- 残した課題
  - 曲を開く処理（Drive では 1〜5 秒）の間は、再生エンジンのワーカーが操作を受け付けない。再生中は先読みで待ちが隠れるようになったが、曲の切り替え直後の一時停止などは遅れる。必要なら、曲を開く処理を別のスレッドに分ける
  - 曲を開くたびに、大きさを得るための問い合わせ（約 0.3 秒）を 1 回している。ライブラリが持つ大きさを渡せば省ける
  - 曲の情報が末尾にあり、大きなアルバムアートが埋め込まれた `.m4a` は、最初の音まで約 5 秒かかる。`曲のキャッシュとオフライン` で、2 回目以降は端末のキャッシュから鳴らす
  - MP3 を途中から読み始めると、最初の約 0.15 秒が無音になる（MP3 のフレームどうしの依存のため）。シークの直後だけなので許容する

### テスト

- 単体テストは中核全体で 55 件、アプリで 1 件、すべて通った。追加は、日時の変換 1 件、Drive の呼び出し 3 件（ページをまたぐ一覧とパスでの検索、部分取得、401 からのやり直しと通信できないとき）、読み込み口 4 件（全体の読み込みとまとめての取得、途中と末尾へのシーク、先読みで待ちが隠れる、エラーと取り直し）、ログイン 4 件、Drive の音楽ソース 3 件、MP3 の見積もり 4 件（3 種類の MP3 で 12.3 秒へのシークの着地を音の高さで確かめる、Drive 越しのシークの通信回数など）
- 資格情報マネージャーへの保存、読み出し、削除を、実際の Windows で確かめた（`cargo test -p cyanomelody -- --ignored`）
- 本物の Drive（`music/cyanomelody_test`、3 曲）で、確認用のプログラムを実行した
  - 手動更新：3 曲を 7.0 秒（タグを並行して読む）。`.m4a` は曲名とアーティストをタグから、WAV と MP3（タグなし）はファイル名から取った
  - 再生（Windows の出力先、音量 0.3 で各曲 3 秒）：WAV は最初の音まで 1.4 秒、曲の 4 割へのシーク 1.2 秒。MP3 は 1.2 秒、シーク 0.07 秒（先読みで取得済み）。`.m4a` は 5.3 秒、シーク 1.0 秒
- Docker で Android 向けにビルドできることを確かめた
